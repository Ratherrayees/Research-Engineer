# Day 003 — BPE Tokenizer Notes

## Goal

Move beyond simple whitespace tokenization and understand how a tokenizer can learn reusable subword pieces from text.

On Day 001 and Day 002, our tokenizer treated complete whitespace-separated words as tokens.

Day 003 introduces a simplified version of:

Byte Pair Encoding (BPE)

The main idea is:

Start with very small units → find common neighboring pairs → merge them → repeat.

---

# 1. Why We Need BPE

Our previous tokenizer had an important limitation.

If the vocabulary knew:

learn

but later received:

learning

learned

learner

then each of those could require completely separate vocabulary entries.

This does not scale well.

Instead, we want reusable pieces.

Conceptually:

learning → learn + ing

learned → learn + ed

learner → learn + er

This allows a finite vocabulary to represent many different words.

---

# 2. What BPE Does

BPE starts with very small pieces.

In our learning implementation, we start with individual characters.

For example:

learning

becomes:

l e a r n i n g

Then BPE repeatedly asks:

Which neighboring pair occurs most frequently?

If:

('i', 'n')

occurs frequently, BPE may merge it:

i + n → in

Now future pair counting treats:

in

as one token instead of two characters.

The process repeats.

---

# 3. The Core BPE Process

Our BPE algorithm follows this pipeline:

Corpus

↓

Split corpus into words

↓

Split each word into characters

↓

Count neighboring pairs

↓

Find the most frequent pair

↓

Merge that pair everywhere

↓

Remember the merge rule

↓

Recount neighboring pairs

↓

Repeat for a fixed number of rounds

↓

Build vocabulary

↓

Assign token IDs

---

# 4. Corpus

BPE needs training text.

The text is called the corpus.

The corpus should contain repeated patterns because BPE learns based on frequency.

For example, if words such as:

learn

learning

learned

learner

appear repeatedly, BPE can begin discovering reusable pieces shared between them.

Important:

BPE is not manually told that "learn" is a root word.

It learns repeated pieces statistically.

---

# 5. Splitting the Corpus into Words

We first split the corpus using whitespace.

Conceptually:

"learn learning learned"

becomes:

[
    "learn",
    "learning",
    "learned"
]

We preserve word boundaries in our simplified implementation.

This prevents BPE from accidentally considering the last character of one word and the first character of another as an internal pair.

---

# 6. Splitting Words into Characters

Each word is then converted into a list of characters.

Example:

learn

becomes:

['l', 'e', 'a', 'r', 'n']

learning

becomes:

['l', 'e', 'a', 'r', 'n', 'i', 'n', 'g']

So our data structure looks approximately like:

[
    ['l', 'e', 'a', 'r', 'n'],
    ['l', 'e', 'a', 'r', 'n', 'i', 'n', 'g'],
    ['l', 'e', 'a', 'r', 'n', 'e', 'd']
]

The outer list contains words.

Each inner list contains the current tokens for that word.

At the beginning, those tokens are individual characters.

---

# 7. Counting Neighboring Pairs

For each word, we inspect neighboring tokens.

For:

['l', 'e', 'a', 'r', 'n']

the neighboring pairs are:

('l', 'e')

('e', 'a')

('a', 'r')

('r', 'n')

We count how many times every pair appears across the corpus.

Conceptually:

('l', 'e') → 12

('e', 'a') → 10

('a', 'r') → 9

etc.

This frequency table tells BPE which pieces commonly occur together.

---

# 8. Finding the Most Common Pair

After counting all neighboring pairs, we find the pair with the highest frequency.

Conceptually:

pair_counts = {
    ('t', 'h'): 25,
    ('i', 'n'): 22,
    ('e', 'r'): 18
}

The most common pair would be:

('t', 'h')

BPE chooses that pair for the current merge round.

---

# 9. Merging the Pair

Suppose the chosen pair is:

('t', 'h')

We combine it into:

th

So:

['t', 'h', 'e']

becomes:

['th', 'e']

Important:

When a pair is merged, we move forward by two positions because both original pieces were consumed.

If no merge happens, we move forward by one position.

---

# 10. Why We Build a New List During Merging

Instead of modifying the original token list while iterating over it, we create a new list.

Conceptually:

Old word:

['t', 'h', 'e']

New word:

['th', 'e']

This avoids changing the structure we are currently traversing.

After the entire round finishes:

new_characters

replaces:

characters

---

# 11. Recounting After Every Merge

Once one pair has been merged everywhere, the token structure changes.

For example:

t + h → th

Now new neighboring pairs can exist:

('th', 'e')

This pair did not exist when everything was still individual characters.

So after each merge, we must:

1. recount all neighboring pairs,
2. find the new most common pair,
3. merge again.

This is why BPE learns progressively larger pieces.

---

('t', 'h')

('th', 'e')

# 13. BPE Does Not Understand Grammar

This is very important.

BPE does not know:

"ing is a suffix"

or:

"learn is a root word"

It only knows:

These neighboring pieces appear together frequently.

If:

i + n

appears frequently, it may become:

in

Then if:

in + g

appears frequently, it may become:

ing

Our output showed exactly this kind of progression. :contentReference[oaicite:4]{index=4} :contentReference[oaicite:5]{index=5}

So BPE discovers useful language pieces statistically.

---

# 14. Merge Rounds

Without a stopping condition, BPE can continue merging until many whole words collapse into single tokens.

We therefore introduced:

rounds

and:

max_rounds

The purpose is to control how many merge operations BPE performs.

Conceptually:

Round 1 → merge most frequent pair

Round 2 → merge next most frequent pair

Round 3 → merge next most frequent pair

...

Stop when maximum number of rounds is reached.

This prevents our learning tokenizer from merging everything indefinitely.

---

# 15. Why the Number of Merge Rounds Matters

Few merge rounds:

characters remain small

↓

more tokens are required to represent text

Many merge rounds:

larger subwords or complete words emerge

↓

fewer tokens may be required

So BPE vocabulary design involves a trade-off between:

Vocabulary size

and:

Sequence length

This is one of the fundamental tokenizer engineering decisions.

---

# 16. Saving Merge Rules

We created:

merge_rules

Every round, we store the pair selected by BPE.

Conceptually:

[
    ('e', 'n'),
    ('t', 'h'),
    ('t', 'o'),
    ('i', 'n'),
    ('e', 'r'),
    ...
]

Our actual BPE run began with learned rules such as:

('e', 'n')

('t', 'h')

('t', 'o')

('i', 'n')

('e', 'r') :contentReference[oaicite:6]{index=6}

These rules are extremely important.

Without saving them, we would only have the final transformed training corpus.

By saving them, we preserve:

what the tokenizer learned.

---

# 17. Why Merge Rule Order Matters

BPE rules are not just a random collection.

The order matters.

Suppose the learned rules are:

1. ('t', 'o') → to
2. ('to', 'k') → tok
3. ('tok', 'en') → token

We cannot directly apply:

('tok', 'en')

before:

tok

exists.

So the tokenizer must apply learned rules in the order they were learned.

This allows larger pieces to be constructed from earlier smaller pieces.

---

# 18. Training the Tokenizer vs Using the Tokenizer

There are now two different phases.

## Training Phase

The tokenizer studies the corpus and learns:

which pairs should be merged.

Output:

merge_rules

and:

vocabulary

## Tokenization Phase

Later, when new text arrives, we do not retrain the tokenizer.

Instead:

New text

↓

break into initial small units

↓

apply previously learned merge rules

↓

produce final tokens

↓

convert tokens to IDs

This distinction is critical.

---

# 19. Building the Vocabulary

After BPE finishes its merge rounds, we inspect the remaining token pieces.

For every unique token, we assign an integer ID.

Conceptually:

th → 0

the → 1

in → 2

ing → 3

token → 4

tokeniz → 5

tokenizer → 6

The exact IDs depend on the order in which our code encounters the tokens.

So our vocabulary still follows:

token → integer ID

just like Day 001 and Day 002.

---

# 20. Encoding

After building the BPE vocabulary, we convert the final token pieces into IDs.

For example:

['learn', 'ing']

might become:

[37, 12]

depending on the vocabulary.

So our tokenizer still performs the same fundamental job:

text → token IDs

The difference is that the tokens are now learned subword pieces rather than only whitespace-separated words.

---

# 21. Important Difference From Day 002

Day 002:

"learning"

might simply be treated as:

learning

one whole word token.

Day 003 BPE:

"learning"

may begin as:

l e a r n i n g

and after learned merges become something like:

learn + ing

The exact result depends on the corpus and merge rules.

---

# 22. Vocabulary IDs Are Still Not Meaning

Even after BPE:

tokenizer → 42

does not mean:

42 = meaning of tokenizer

The number is still only an identifier.

The later pipeline remains:

Text

↓

BPE tokenizer

↓

Token IDs

↓

Embedding lookup

↓

Embedding vectors

↓

Neural network

The tokenizer determines the pieces.

The neural network learns representations and relationships.

---

# 23. Important Limitation of Our Current Implementation

Our simplified BPE implementation begins from characters and keeps words separated.

Real modern LLM tokenizers may operate differently.

Many use byte-level or other subword approaches.

Whitespace may itself participate in tokenization.

Unicode, punctuation, normalization, special tokens, and fallback mechanisms also require more sophisticated handling.

Our Day 003 implementation is therefore:

a learning BPE tokenizer

not a production tokenizer.

Its purpose is to expose the actual algorithm.

---

# 24. Another Limitation: Reconstruction

Our current encoded token IDs are flattened into one sequence.

Because we split the corpus into words first and did not encode explicit spaces as tokens, exact original word boundaries are not fully represented in the final flattened token ID list.

That means exact decoding/reconstruction requires additional handling.

Real tokenizers solve this by representing whitespace or boundaries in their encoding scheme.

We will not over-engineer this learning tokenizer yet.

# 27. Core Mental Model of BPE

BPE asks:

Which neighboring pieces repeatedly occur together?

Then:

merge them into a larger reusable piece.

Repeat this many times.

So:

characters

↓

frequent character combinations

↓

subwords

↓

sometimes complete common words

The tokenizer does not understand language grammar directly.

It discovers useful pieces based on statistics.

---

# 28. The Most Important Concept From Day 003

The tokenizer vocabulary does not need to contain every possible complete word.

Instead, it can contain reusable pieces that combine to represent new words.

This helps solve the central tokenizer problem:

How can we represent an enormous and constantly changing language using a finite vocabulary?

BPE answers:

Build useful reusable pieces from frequently occurring combinations.
